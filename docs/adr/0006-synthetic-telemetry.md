# ADR-0006: Synthetic telemetry, never a real aviation data feed

**Status:** Accepted

## Context

The system needs a continuous stream of aircraft position reports. Real feeds
exist — ADS-B aggregators, commercial flight-tracking APIs — and using one would
make the dashboard show real aircraft.

## Decision

All telemetry is generated by the simulator in `packages/simulator`. The project
ingests no real aircraft data and connects to no aviation data provider.

## Why

**A demo must not depend on someone else's uptime.** A walkthrough that fails
because a third-party API is rate-limiting, or because the room's wifi is
captive-portalled, is a walkthrough that failed.

**Failure scenarios have to be reproducible.** Demonstrating an engine
over-temperature alert requires an aircraft with an over-temperature. Waiting for
a real one is not a plan.

**Licensing.** Most aviation data feeds restrict redistribution. An open-source
repository that ships an integration with one either carries those terms or
invites users to violate them.

**It stays unambiguously a reference implementation.** Synthetic operators with
invented names cannot be mistaken for a service publishing data about a real
carrier's fleet.

## What the simulator does

Aircraft fly real great-circle routes between real airports in British Columbia
and Alberta, with a flight model of taxi, climb, cruise, descent and landing.
Speeds, altitudes and fuel burn come from per-type reference data. On arrival an
aircraft turns around and picks a new destination.

The fleet is deterministic: the generator is seeded, so the same seed produces
the same fleet every run. A demonstration can be rehearsed, and "it looked
different last time" is a real signal rather than the generator being random.

Reports go to the ingest API over HTTP. The simulator has no special path into
the system — see [ADR-0007](0007-demo-mode-is-production-shaped.md).

## Consequences

- Nothing on the dashboard is a real aircraft, and the README says so.
- The simulator is a load generator, not part of the application. It is disabled
  by default in the Helm chart and gets no AWS permissions.
- Adding a real feed later would mean another producer posting to the same ingest
  endpoint. Nothing downstream would change, which is a reasonable proof that the
  boundary is in the right place.
