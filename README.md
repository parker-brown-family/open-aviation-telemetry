# Open Aviation Telemetry

[![CI](https://github.com/parker-brown-family/open-aviation-telemetry/actions/workflows/ci.yml/badge.svg)](https://github.com/parker-brown-family/open-aviation-telemetry/actions/workflows/ci.yml)
[![License](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)

An open-source AWS reference architecture for aircraft telemetry: ingest position
reports over HTTP, publish them to Kafka, derive alerts in a stream processor,
generate reports on a queue worker, and show the whole thing on an operations
dashboard that explains itself.

The system runs end to end on a laptop with one command. Every AWS resource it
would use in a cluster is described in Terraform, and every workload in a Helm
chart.

```
make demo
```

Dashboard on <http://localhost:3000>, API docs on <http://localhost:8080/docs>.

---

## Why this exists

Reading about Kafka partitioning is not the same as watching consumer lag climb
during a burst and drain again. Reading about dead-letter queues is not the same
as clicking a button, watching a job fail three times, and finding it in the DLQ.

So this is a small system built to be **operated**, not just read: it has a
failure-injection console, real metrics rather than display values, and an
architecture page that answers "why this and not that" for every component.

Aviation telemetry is the domain because it produces genuinely useful
architectural pressure — a continuous high-volume stream, per-aircraft ordering,
derived safety alerts, and slow analytical work that must not block ingestion.

**This project is not affiliated with any aviation company.** All aircraft,
operators and telemetry are synthetic and generated by the simulator in this
repository. It ingests no real aircraft data and connects to no aviation data
provider.

## The path one telemetry report takes

```
  aircraft (simulated)
        │  POST /api/v1/telemetry
        ▼
  ┌─────────────────┐   validate → publish → project → 202
  │  Telemetry API  │───────────────────────────────────┐
  └────────┬────────┘                                   │
           │ publish, keyed by aircraft_id              │ upsert current state
           ▼                                            ▼
  ┌─────────────────┐                          ┌──────────────────┐
  │  Kafka          │                          │   PostgreSQL     │
  │  aircraft.      │                          │  aircraft        │
  │  telemetry.v1   │                          │  telemetry_latest│
  └────────┬────────┘                          │  telemetry_history│
           │ consumer group                    │  alerts          │
           ▼   telemetry-processors            │  reports         │
  ┌─────────────────┐   dedupe → history →     │  processed_events│
  │ Stream processor│   flight phase → alerts ─▶└──────────────────┘
  └─────────────────┘                                   ▲
                                                        │
  POST /aircraft/{id}/reports                           │
        │                                               │
        ▼                                               │
  ┌─────────────────┐   enqueue   ┌─────────────────┐   │
  │  Telemetry API  │────────────▶│  RabbitMQ       │   │
  └─────────────────┘             │  report.generate│   │
                                  └────────┬────────┘   │
                                           │ prefetch=1 │
                                           ▼            │
                                  ┌─────────────────┐   │
                                  │  Report worker  │───┘
                                  └─────────────────┘
                                     retry ×3 → DLQ
```

Three decisions carry most of the design, and each has an ADR:

**The stream is the system of record.** The API publishes to Kafka _before_
writing to PostgreSQL. The current-state row is a projection: if that write
fails, the event still exists, the stream processor still writes history, and
the next report repairs the projection. Doing it the other way round would let
the database record a report no consumer ever sees.

**Messages are keyed by `aircraft_id`.** Every report for one airframe lands on
one partition and is processed in order; different airframes process in
parallel. That is also what makes it safe for the stream processor to keep
per-aircraft state in memory — a partition has exactly one consumer in a group.

**Kafka and RabbitMQ are not interchangeable.** Kafka carries _facts_
("this aircraft reported this position") — replayable, readable by any number of
consumers. RabbitMQ carries _commands_ ("generate this report") — acknowledged,
retried, dead-lettered. Using one for both means rebuilding the other's
semantics by hand. See
[ADR-0005](docs/adr/0005-rabbitmq-for-work-items.md).

## Run it

Requirements: Docker, Node 20+, pnpm.

```bash
git clone https://github.com/parker-brown-family/open-aviation-telemetry
cd open-aviation-telemetry
make demo
```

That builds five images, starts PostgreSQL, Kafka and RabbitMQ, runs the
migrations, waits for readiness and starts the simulator at ten aircraft.

Then prove it actually works:

```bash
make smoke
```

The smoke test asserts each stage from the outside — including that telemetry
history exists, which only the Kafka consumer writes, so a pass means the event
genuinely crossed the broker.

| Command                    | What it does                                            |
| -------------------------- | ------------------------------------------------------- |
| `make demo`                | Start everything and run the simulator                  |
| `make smoke`               | Prove the pipeline works end to end                     |
| `make e2e`                 | Run the full end-to-end suite against the running stack |
| `make busy` / `make burst` | 100 aircraft; then four reports per second              |
| `make status`              | Container status and the readiness breakdown            |
| `make logs`                | Follow every service                                    |
| `make down`                | Stop everything and delete the data                     |

## What to look at

**Dashboard** — <http://localhost:3000>. Fleet counts, consumer lag, queue
depth, request latency. Every number is measured from the running system.

**Architecture explorer** — <http://localhost:3000/architecture>. Click any
component for what it is, why it is here, what was considered instead, how it
fails, how it scales, and which files implement it. The **guided tour** walks one
telemetry report through the whole system.

**Demo console** — <http://localhost:3000/demo>. Fault injection:

| Scenario                | What it demonstrates                                                 |
| ----------------------- | -------------------------------------------------------------------- |
| Engine over-temperature | Raw telemetry becoming a derived alert                               |
| Rapid descent           | A rule that needs vertical rate, not just position                   |
| Telemetry gap           | Absence of data treated as information — active, stale, lost         |
| Report worker failure   | RabbitMQ retry through a delay queue, then dead-lettering            |
| Poison event            | An unprocessable message quarantined instead of stalling a partition |

Injections change what the aircraft _reports_. The anomalous reading then travels
the same path as every other report, so the alert you see was genuinely derived —
not written there by the button.

**API documentation** — <http://localhost:8080/docs>, generated from the routes.

## Repository layout

```
packages/
  shared/              Contracts: telemetry schema, event envelope, job
                       definitions, alert thresholds, geodesy. Browser-safe.
  data/                One SQL data layer, shared by the three services that
                       talk to PostgreSQL. Plus the migrations.
  service-kit/         Logging, metrics, probe server, graceful shutdown,
                       Kafka and RabbitMQ setup shared across services.
  telemetry-api/       Fastify. Ingest, fleet reads, report requests, demo control.
  telemetry-consumer/  Kafka consumer. Dedupe, history, flight phase, alerts.
  report-worker/       RabbitMQ consumer. Flight summaries, retry, dead-lettering.
  simulator/           Synthetic fleet flying real routes around BC and Alberta.
  web/                 React dashboard, architecture explorer, demo console.

infra/
  terraform/           Canonical infrastructure: VPC, EKS, RDS, MSK, Amazon MQ,
                       ECR, IAM, CloudWatch.
  cdk-reference/       The same network and registry in AWS CDK, for comparison.
                       Manages nothing — see ADR-0001.

charts/                Helm chart for all five workloads.
tests/e2e/             End-to-end suite; needs a running stack.
docs/adr/              Architecture decision records.
```

Contracts live in `packages/shared` and are imported by the services _and the web
client_. The Architecture Explorer displays the same alert thresholds and topic
names the stream processor evaluates, so the documentation on that page cannot
drift away from the implementation — there is a test that asserts it.

## Tests

```bash
pnpm test          # unit and component suites, no I/O
make e2e           # end-to-end, against a running stack
```

Three layers, on purpose:

- **Unit** — the pure logic: telemetry validation, anomaly rules, flight-phase
  derivation, geodesy, the consumer's replay and ordering guards, report
  arithmetic, retry policy.
- **Component** — the web client under jsdom. Most importantly the data-source
  layer, because a regression there could let the published page show sample
  numbers without saying so.
- **End-to-end** — the real system over HTTP only, with no database or broker
  client of its own. An assertion can only pass if the real pipeline ran.

The end-to-end suite is separate from `pnpm test` deliberately: a failure there
should mean "the code is wrong", never "Docker is not running".

CI runs all three. The end-to-end job brings up PostgreSQL, Kafka, RabbitMQ and
all four services on a GitHub Actions runner and asserts the pipeline from the
outside — so the badge above means the architecture works, not just that it
compiles.

## Deploying to AWS

Terraform is the canonical implementation and owns every deployed resource.

```bash
make tf-validate    # fmt + validate, no credentials needed
make tf-plan        # what would be created
make tf-apply       # create it — this costs money
make destroy        # remove it
```

It creates a VPC across two AZs, an EKS cluster with a managed node group, RDS
PostgreSQL, MSK Serverless, Amazon MQ for RabbitMQ, ECR repositories, CloudWatch
log groups, and one IAM role per application bound through EKS Pod Identity.

Costs roughly **US$20–35 per day** while running, most of it the EKS control
plane, the NAT gateway and Amazon MQ. Run `make destroy` when the demo is over.
Provisioning takes about 25 minutes; the RabbitMQ broker alone takes ~15.

There are no static AWS credentials anywhere: MSK authenticates the pod's own IAM
role over SASL/OAUTHBEARER, and database and broker passwords are generated by
Terraform straight into Secrets Manager, never passed as variables and never
printed as outputs.

Full walkthrough in [docs/aws-deployment.md](docs/aws-deployment.md).

## The published demo page

A build of the client is published at
<https://parker.brownfamilysports.com/aircraft-telemetry/>. **No API is attached
to it.**

That page detects it cannot reach an API and says so in a permanent banner, then
renders a bundled sample dataset so the architecture explorer is still usable.
Write controls are disabled rather than appearing to work.

This is deliberate. A dashboard showing plausible fabricated numbers without
saying so is worse than one showing nothing, so the distinction is carried in the
payload itself — the infrastructure endpoint returns `simulated: true` when its
figures are placeholders — and there are tests that assert the banner appears.

Run it locally to see real measured data.
